## 2. 分阶段计时

未使用每帧堆分配。`World` 内新增固定数组：

```cpp
struct PhaseStat { double ms = 0.0; uint64_t calls = 0; };
std::array<PhaseStat, PhaseCount> phaseStats_{};
```

每个阶段用 `std::chrono::steady_clock` 计一次，累计到固定槽位；`World::resetPhaseStats()` 在预热后清零。拆出的阶段：

`total`、`ships`（总）、`ship_decide`、`ship_scan`、`asteroids`、`lights`、`beams`、`zones`、`rebuild_grids`、`collisions`、`collect_lights`、`building`、`rebellion`、`trails`、`cleanup`、`flush_requests`、`spawning`、`active_count`。

另外增加了累计计数：`shotsFired`、`shipDeaths`、`asteroidDeaths`，用于确认战斗强度没有被场景改动偷掉。

输出方式：
- `--bench ...` 直接打印阶段表；
- `--bench-csv PATH` 追加一行完整 CSV（含每个阶段的 `avg_ms`）；
- `--bench-verify-grid` 校验最近邻搜索。

阶段计时本身在 8000 艘时约增加 0.02–0.05ms/步，对结论无影响；before/after 都带同一套计时。

## 6. 已实现优化 1：独立碰撞网格（采用）

### 做法

`rebuildGrids()` 中同时维护一个只服务飞船-飞船碰撞的 `collisionGrid_`：

```cpp
shipGrid_.init(..., 100.0f);       // AI/目标查询，保持 100px
collisionGrid_.init(..., 40.0f);   // 仅碰撞，40px
...
collisionGrid_.insert(i, s.pos, SHIP_RADIUS + 1.0f);
...
collisionGrid_.query(a.pos, SHIP_RADIUS * 2.0f + 2.0f, ...);
```

碰撞查询半径只有 12px。原来 100px 网格一次查询要扫 1–4 个 cell，每个 cell 在 8000 艘时约 80 个候选；40px 网格把候选数降到约 1/6。代价是重建时多插一遍飞船（+0.34ms/步），但碰撞节省远大于此。

### 单独测量（8000 艘，同一会话，未加最近邻优化）

| 指标 | 原 100px 单网格 | 独立 40px 碰撞网格 | 变化 |
|---|---:|---:|---:|
| avg | 17.72 ms | **13.73 ms** | -22.5% |
| collisions | 7.597 ms | **4.262 ms** | -43.9% |
| rebuild_grids | 0.378 ms | 0.571 ms | +0.193 ms |
| ship_decide | 5.348 ms | 4.801 ms | 噪声内 |
| ship_scan | 1.591 ms | 1.510 ms | 噪声内 |

结论：**采用**。最终版本与最近邻优化合并后，8000 艘碰撞 8.402 -> 4.761ms。

### 未采用的网格尺寸

| 试验 | avg 8000 | collisions | 结论 |
|---|---:|---:|---|
| 碰撞网格 32px | 18.79 / 18.26 ms（两次） | 5.37 / 5.40 ms | **不采用，变慢**。cell 太多（约 5100 个 vector），重建和缓存污染抵消了候选减少。 |
| 只把 AI `shipGrid_` 改成 50px | 17.02 ms（基线同会话 16.4） | 5.21 ms | **不采用，变慢**。碰撞略降，但 AI 查询从 25 个 cell 涨到约 100 个 cell，`ship_decide` 6.48 -> 8.19ms。 |

## 7. 已实现优化 2：精确环形最近邻（采用）

### 做法

`evaluateState()` 原来对每个飞船做：

```cpp
shipGrid_.query(s.pos, s.viewRange, ...);   // 扫 5x5 个 100px cell
```

改为 `Grid::nearest()`：

- 从飞船所在 cell 开始，按 Chebyshev 环向外扫描；
- 维护当前最优距离 `bestDistSq`；
- 每扫完一环，计算“未扫描区域到飞船的距离下界” `outside = min(dx, dy)`；
- 若 `bestDistSq <= outside²`，立即停止——任何未扫 cell 都不可能更近；
- 仍然用 stamp 去重，返回严格最近的有效实体。

这是**精确最近邻**，不是“找到第一个敌人就返回”。敌机、光点、小行星三条查询都改用它。

### 正确性验证

新增 `--bench-verify-grid`：

- 4000 个实体，按真实 6px 插入半径写入网格；
- 60000 次随机查询，查询半径混合 12px 和 220px；
- 与 4000 个实体的暴力枚举逐次比较最近距离和返回索引；
- 结果：

```text
grid_verify entities=4000 queries=60000 found=54500 mismatches=0
```

60,000 次全部一致，0 mismatch。实际运行中 8000 艘的最终死亡数 486 -> 487、开火数 60,087 -> 59,791，差异来自 tie-break 和碰撞顺序，不是漏检。

### 效果（8000 艘，未叠加碰撞网格时）

| 指标 | 原全 grid 扫描 | 环形最近邻 | 变化 |
|---|---:|---:|---:|
| avg | 13.73 ms | **9.98 ms** | -27.3% |
| ship_decide | 4.80 ms | **0.96 ms** | -80.0% |
| ship_scan | 1.51 ms | 1.49 ms | 基本不变 |

最终版本与碰撞网格合并（固定 CPU、中位数）：

| 指标 | before | after | 变化 |
|---|---:|---:|---:|
| total 8000 | 19.012 ms | **11.227 ms** | **-40.9%** |
| AI（decide+scan） | 7.252 ms | **2.673 ms** | -63.1% |
| collisions | 8.402 ms | **4.761 ms** | -43.3% |

结论：**采用**。

## 8. 是否建议多线程

**当前不建议实现线程池。先做算法优化，收益更高、风险更低。**

优化后 8000 艘的阶段预算：

| 阶段 | 占比 | 可否并行 | 主要约束 |
|---|---:|---|---|
| collisions | 42.6% | 很难 | 同一对飞船互相写位置/速度；解析顺序影响结果。需要空间着色/分块或延迟冲量，复杂且难复现。 |
| 飞船移动/控制 | 19.8% | 可以 | 每艘船只写自己的 `Ship`；但 `rng_` 共享、建筑请求 `shipRequests_` 共享。 |
| ship_scan | 14.2% | 可以 | 只读网格/小行星；但 `Grid::query` 会改 `queryId_` 和 `stamp_`，**当前不可并发读**。 |
| ship_decide | 9.8% | 可以 | 只读网格；写自己的目标字段。开火会写 `beams_`、目标血量、`history_`，必须延迟。 |
| rebuild_grids | 6.8% | 可以 | 四张网格可并行建，或按 cell 分块；但占比小。 |
| collect_lights | 4.4% | 有限 | 竞争同一光点 `active` 和 `resources_`；需要 per-light claim/原子。 |
| 其余 | 2.4% | 否 | 量小，串行即可。 |

### 预计 4 核收益

用 Amdahl 估算：串行下限至少是 collisions 42.6% + 其他 ~2.4%，即约 45%。即使把剩余 55% 做到接近 4 核理想：

- 理想上限约 **1.7x**；
- 考虑任务粒度、每帧同步、per-thread 网格 stamp、延迟事件合并，现实收益约 **1.30–1.45x**（8000 艘）；
- 2000–4000 艘约 **1.15–1.30x**；
- 500 艘单步已低于 1ms，线程启动/同步可能直接负优化。

### 必须先解决的风险

1. `Grid::query()` 的 `queryId_`/`stamp_` 是共享可变状态；并行只读网格目前**不安全**，需要每线程 stamp 或只读快照。
2. `World::rng_` 是单实例 `std::mt19937`，多线程调用会数据竞争且破坏可复现性；必须 per-thread RNG + 固定种子拆分。
3. `fireAtShip` 直接改目标飞船、`beams_`、`history_`、`kills`/`title`；并行 AI 只能生成**伤害/开火事件**，串行合并。
4. `collectLights` 直接改 `lights_[i].active` 和 `resources_`；同一光点可能被多艘船同时收集。
5. `cleanup()`/`freeShips_`/`spawnShipFragments()` 依赖单线程顺序，不能与 `updateShips` 重叠。
6. 确定性：当前单线程结果可复现；并行归约顺序会改变 tie-break 和 p95。若要做，建议先定义“事件按 (shipIndex, eventSeq) 排序后串行应用”的确定性模型。

**建议**：先继续做 collisions 的空间分块/半邻域配对，以及 `collectLights` 的反向遍历；等单线程降到 7ms 以下再考虑线程，届时串行占比更高，线程收益更小。

## 9. 建议汇总

| 项 | 结论 |
|---|---|
| 独立 40px 碰撞网格 | **采用**，8000 艘碰撞 -43.9%，净总时间 -22.5%（单独测试） |
| 精确环形最近邻 | **采用**，决策阶段 -80%，和碰撞网格合并后 8000 艘总时间 -40.9% |
| 碰撞网格 32px | **不采用**，实测 18.8ms，慢于 40px 的 13.7ms（同会话） |
| AI 网格改 50px | **不采用**，AI 查询 cell 数增加，实测 17.0ms 慢于 16.4ms |
| 4 核线程池 | **暂不实现**，现实收益 1.3–1.45x，风险/复杂度高；先做串行算法优化 |

最终建议：把这两个优化作为下一步主线；碰撞仍是最大单阶段（42.6%），下一项应优先研究**半邻域碰撞配对/按 cell 分块**，而不是先上线程。

## 10. 未验证 / 不能声称的部分

以下没有实测，报告中不当作结论：

- 10,000 艘以上、更极端密度、不同种子/不同地图；本次只测 500/2000/4000/8000。
- 游戏窗口渲染、VSync、实际 FPS；所有数据都是无窗口 `--bench` 固定步长。
- 真实 4 核线程池的吞吐和 p95；第 8 节只是基于阶段占比的设计估算，**未实现、未跑**。
- 其他 CPU 架构、冷暖缓存、长时间运行（>5 秒）和内存增长。
- 32px/40px 之外的碰撞网格尺寸（24/48/56px）未系统扫参。
- before/after 不是逐位相同：碰撞配对顺序与最近邻 tie-break 改变，开火/死亡数有 0.5%–3% 差异；只声称“战斗强度可比”，不声称“bit-identical”。
